A tight lookup loop burns full CPU.
Your array fits completely inside L3 cache.
Yet binary search branch mispredictions silently waste dozens of cycles on every comparison step. ⚠️

A branch misprediction occurs when the hardware guesses which direction a conditional branch will take, speculatively runs ahead, and turns out to be wrong.

Here is where it bites:
→ Running uniform random queries across a sorted array
→ Searching millions of rows in an in-memory column store
→ Seeing CPU cycles surge while memory throughput stays low

Modern out-of-order processors keep execution units saturated by predicting jump outcomes dozens of steps in advance. Binary search breaks this hardware optimization completely. Because a lookup value is just as likely to land above the middle element as below it, the branch history table sees pure coin flips.

Whenever the CPU guesses wrong, it triggers a full pipeline flush, tossing out speculatively decoded instructions and reloading from scratch. The comparison itself costs one clock cycle, but recovering from the mispredicted branch costs up to twenty cycles.

Rewriting the search to use conditional move instructions like CMOV lets the core calculate the next offset arithmetically without jumping, cutting search latencies by up to sixty percent.
