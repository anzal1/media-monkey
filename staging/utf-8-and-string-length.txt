A single emoji entered into an input field.
The database varchar limit throws an overflow error.
Your frontend code thought it was one character, but UTF-8 and string length calculations just disagreed.

Unicode assigns every character a scalar number, but modern encodings pack those numbers into variable slices of memory.

Picture this:
➔ A frontend length check returns two for a single laughing face
➔ A slice index cuts an encoded sequence right down the middle
➔ The database truncates the raw bytes and leaves an invalid character

When you ask JavaScript for string length, it returns the count of sixteen-bit code units, not graphemes. If your code point sits beyond the basic multilingual plane, the runtime splits it across surrogate pairs. That means your single emoji is already length two.

Over the wire, UTF-8 encodes that same value using four physical bytes. If that emoji joins another symbol using a zero-width joiner, the single glyph on your screen can easily balloon into eleven bytes across multiple distinct code points.

Slicing a string by naive array offsets breaks the multi-byte sequence, producing corrupted replacement characters across your logs and corrupting database rows.
