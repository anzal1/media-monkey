Your test suite is green.
Your background worker crashes on missing records.
Classic transaction rollback testing hides this exact bug.

Transactional test fixtures isolate test cases by wrapping every execution block in an open transaction that rolls back at teardown.

Picture this:
→ The test inserts a new user record inside an uncommitted database transaction.
→ The app enqueues an asynchronous welcome email job with that record ID.
→ The background worker runs in a separate database session and finds nothing.

Under default read committed isolation, dirty writes remain strictly invisible to concurrent connections. Because the worker operates over a distinct connection from the test runner, it queries for a primary key that does not yet exist outside the runner's private transaction buffer.

In production, this surfaces as an intermittent race condition whenever Redis outruns your database commit. Inside a rollback test, that record is never committed at all, turning every real worker assertion into a false negative.

Catch this by running asynchronous integration specs against truncated tables, or bind background job dispatches strictly to post-commit lifecycle callbacks.
