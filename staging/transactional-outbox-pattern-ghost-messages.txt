Skipping the transactional outbox pattern creates phantom traffic 👻

The dual-write problem occurs whenever your application tries to update an external message broker and a relational database inside the same code block without a shared consensus coordinator.

Here is where it bites:
→ You publish a message to the broker right after inserting the row.
→ The broker forwards that payload to background workers immediately.
→ A unique constraint fails and rolls the database transaction back.

Your message queue cannot roll back across the network once the bytes are sent. The broker already told downstream consumers to charge the card, send the welcome email, and reserve warehouse inventory for a transaction that never actually committed.

Fixing it requires writing the message directly into an outbox table in the exact same atomic transaction as your core business entities. A relay process like Debezium then tails the write-ahead log to emit the message to Kafka safely after commit.

A single ghost order during peak traffic leaves orphan state that takes hours of manual customer support and database patching to reconcile.
